## 3. Findings register

- **F1 — Local build gate not reproducible as written.** Spec §4.1 says `npm run build` runs "against file: DB (env from `.env.test`)" — **no `.env.test` exists** (only `.env.local`). A naive `npm run check`-then-`build` fails: `SQLITE_ERROR: no such table: paintings` (verbatim, this session). The working procedure (DECISIONS 028) is a shell-level `TURSO_DATABASE_URL=file:./ci.db`. _Disposition:_ gates.json encodes the env var explicitly in every build gate; BUILD-SPEC documents it as the canonical command.
- **F2 — Baseline `npm run check` was RED at audit start.** `format:check` failed on the untracked `SCOPE.md`. Fixed in-audit (`prettier --write SCOPE.md`); suite green after. Lesson kept: prettier checks untracked root files, so any operator-authored root doc can redden the gate.
- **F3 — R4 tag missing** (Spec §14: every milestone tagged). _Disposition:_ M0 work item — tag `R4` at `2c9f15e` (operator-authorized push).
- **F4 — Local `main` was stale (12 behind).** Fixed in-audit via `git fetch` + ff-only merge. No divergence, no local-only commits.
- **F5 — Default-branch conflict (Gate 1 ruling required).** Repo default is `main`; CI triggers on `main`; Vercel production builds from `main`; remote HEAD is `main`. Operator's standing rule elsewhere is `master`-only. **Recommendation: keep `main` through v1.0.0** — renaming a live wired branch mid-ship risks CI triggers, Vercel production-branch config, and open PR bases for zero functional gain; revisit post-ship if desired. Not renamed unilaterally per SCOPE.
- **F6 — Documented backup ritual is non-executable on this machine.** OPERATOR-GUIDE §R1 step 1 and the "Standing queries" section use `turso db shell` — the Turso _cloud_ CLI is **not installed** (verified: `where turso` → not found; only `~/.turso/tursodb.exe`, the local server). R4's real backups were taken via `@libsql/client`. _Disposition:_ M0 ships `scripts/backup-prod.ts` (read-only dump → `backups/`, libsql path) so the backup-first ritual has a runnable command; OPERATOR-GUIDE Chuck addendum notes the substitution.
- **F7 — Backup coverage and restore fidelity are unproven.** `backups/` holds JSON dumps of exactly two tables (`paintings`, `trail_progress`, 2026-07-06). Never backed up: `users`, `sessions`, `accounts`, `murals` (if table), `trail_completions`, tag tables. **No restore procedure exists or has ever been tested.** _Disposition:_ M0 backup script covers all app tables; restore procedure documented + dry-tested against a local file DB in M0.
- **F8 — `npm run db:push` is a loaded gun.** `drizzle-kit push` reads `.env.local` (dotenv in `drizzle.config.ts`). Normally that targets `file:./dev.db`, but the moment prod creds are uncommented (exactly the state during content-loop and migration ops), `db:push` targets **live production** — the precise act Iron Rule 1 bans. _Disposition:_ VETO POINT in DECISIONS — recommend replacing with `db:push:dev` guarded to refuse `libsql://` URLs (M0).

Script guards otherwise good (`--dry-run` default, `--apply` explicit, export refuses overwrite without `--force`). _Disposition:_ M2 human-hands protocol makes the backup a recorded, dated step gated before `--apply`; M0's backup script makes it one command.
